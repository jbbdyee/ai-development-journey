# tcrew SPEC

근거: 초기 요청서와 요구 비교 문서. R1~R5는 구현·테스트 기준이며, 4절과 마지막 비교 결과는 당시의 작업 순서를 기록한다. 현재 동작과 남은 제한은 5절 및 [README.md](README.md)에 정리했다.

## 1. 요구 (확인할 수 있게)

| 번호 | 요구 | 요청의 어느 말 | 확인 방법 (파일 · 숫자 · 화면) |
| --- | --- | --- | --- |
| R1 | 질문 하나를 받아 `crew.yaml`에 적힌 역할의 이름·지시문·받는 것에 따라 순서대로 실행한다. 기본 역할은 작성자 → 검토자 → 정리자이며, 뒤 역할의 입력에는 앞 역할의 산출물이 포함된다. | ①, “터미널에서 바로” | `uv run tcrew "질문" --plain`에서 역할별 답을 글자로 확인한다. 가짜 LLM 호출 순서가 `writer, reviewer, editor`인지, 검토자 입력에 초안이, 정리자 입력에 앞 단계 글이 있는지 검사한다. |
| R2 | Textual TUI에서 역할별 답과 소요 시간을 별도 탭으로 보여 준다. 탭 제목에는 역할 이름·대기/실행 중/완료/실패 상태·초 단위 시간이 있고, 질문 입력칸이 있다. LLM 실행 중에도 화면과 입력이 멈추지 않으며 완료된 역할부터 탭을 채운다. | ② | 가짜 LLM 응답 세 개로 실행해 세 탭의 제목·본문·시간을 각각 확인한다. 응답을 지연시키는 가짜 LLM으로 실행 중 화면 조작이 가능하고 첫 역할 완료 후 다음 역할 완료 전 첫 탭에 결과가 표시되는지 확인한다. |
| R3 | 검토자의 첫 줄 `PASS`/`FIX`와 그 뒤의 의견을 읽어 판정한다. `FIX`이면 작성자는 **처음 질문·이전 초안·검토 의견**을 받아 `crew.yaml`의 `max_revisions: 1`에 따라 한 번만 재작성한 뒤 재검토한다. 지정된 미완성 대괄호 표제가 초안에 남아 있으면 Reviewer 원문이 `PASS`여도 유효 판정을 `FIX`로 바꾼다. 재검토도 통과하지 못하거나 응답이 누락·손상·해석 불가이면 성공으로 표시하지 않고 멈춰 사유를 알린다. | ③ | 항상 `FIX`를 반환하는 가짜 검토자로 실행한다. 작성자 2회, 검토자 2회, 총 4회 호출 뒤 성공 없이 종료하고 재작성 입력의 세 요소를 검사한다. 잘못된 검토 응답의 실패 처리와 원문 `PASS`·플레이스홀더·재검토 실패 경로를 각각 확인한다. 일반 대괄호 제목은 차단하지 않는지 검사한다. |
| R4 | 역할 지시문·목록·입력 대상을 `crew.yaml`에서 읽는다. YAML만 수정해 기존 역할의 지시문을 바꾸거나 새 역할을 추가할 수 있다. | ④ | 코드 변경 없이 YAML 지시문을 바꾸면 다음 실행의 해당 LLM 입력이 달라지는지 확인한다. `translator`를 추가하면 지정 위치에서 호출되고 앞 결과를 받으며 TUI 탭이 4개로 늘어나는지 확인한다. |
| R5 | 실행마다 역할별 입력·출력·소요 시간과 재검토를 포함한 실행 기록을 `runs/*.json`에 남긴다. | ⑤ | 두 번 실행한 뒤 두 JSON 기록이 남고 각 기록에서 역할 이름·입력·출력·시간, 검토 의견과 재검토 결과를 찾을 수 있는지 확인한다. 실패한 실행도 기록되는지 확인한다. |

### 공통 합격 조건

- `OPENAI_API_KEY`는 환경 변수에서만 읽는다. 코드, `crew.yaml`, 터미널 출력, `runs/*.json`에 키 문자열이 없는지 임의의 시험용 키로 확인한다.
- 자동화 테스트는 진짜 LLM API를 호출하지 않는다. 가짜 LLM으로 모든 분기와 호출 횟수를 확인하며, 테스트 실행 중 네트워크 호출이 없음을 확인한다.
- 실제 LLM을 쓰는 수동 실행은 키가 있을 때 `gpt-4.1-mini`로 동작하는지 확인한다. 이 검증은 유료 호출이므로 자동화 테스트에는 포함하지 않는다.

## 2. 숨은 요구 (요청에 직접 없지만 없으면 안 되는 것)

- 검토 결과에는 기계가 판정할 수 있는 계약이 필요하다. 이번 실습은 첫 줄 `PASS`/`FIX`로 판정하고 나머지를 의견으로 전달한다. 기존 n8n의 `passed`, `codes`와의 변환은 이번 범위에 없다.
- 재작성 입력에는 처음 질문, 직전 초안과 검토 의견이 모두 필요하다. 그래야 원래 사실을 유지하며 검토 결과에 따라 글을 바꿀 수 있다.
- 역할별 입력·출력·소요 시간·상태를 한 실행의 데이터로 묶어야 화면과 기록이 같은 사실을 보여 줄 수 있다. 재작성과 재검토의 결과도 첫 시도와 구분되어야 한다.
- 검토 응답이 모호하거나 LLM 호출이 실패했을 때의 종료 상태가 필요하다. 어느 경우에도 성공으로 기록해서는 안 된다.
- 설정 파일을 읽을 수 없거나 필수 역할·지시문이 빠진 경우, LLM을 부르기 전에 사용자가 수정할 수 있는 오류를 보여 줘야 한다.
- 터미널 실행에는 질문 문자열과 결과·실패 상태를 알 수 있는 인터페이스가 필요하다. 출력과 기록에는 키를 포함한 비밀값이 섞이지 않도록 해야 한다.
- LLM 호출 중 TUI가 멈추지 않도록 비동기로 실행하고, 완료된 역할의 탭을 즉시 갱신해야 한다.
- 추가 역할도 기존 역할과 같은 설정·실행·표시·기록 경로를 사용해야 한다. 새 역할마다 코드를 고쳐야 한다면 ④를 만족하지 못한다.

## 3. 범위 밖 (이번 실습에서 구현하지 않을 것)

- n8n 워크플로우와 직접 연결하거나 기존 노드를 수정하는 기능
- 여러 요청을 한꺼번에 실행하는 배치·병렬 처리
- 역할별로 서로 다른 LLM 제공업체나 모델을 선택하는 기능
- 웹 화면, 사용자 계정, 원격 기록 검색 서비스
- 무제한 수정 루프 또는 사람이 개입하는 승인 절차

## 4. 만드는 순서 (그리고 그 이유)

1. **입력·설정·검토 응답 계약을 정하고 읽기**: 역할 목록과 판정 규칙이 뒤 단계의 공통 기준이다. 확인 필요 항목을 먼저 검토한 뒤 파일 형식과 오류를 검증한다.
2. **가짜 LLM으로 순차 실행과 역할별 결과 만들기**: R1을 먼저 충족해 이후 화면·기록이 사용할 동일한 실행 데이터를 만든다.
3. **검토 판정·한 번의 재작성·JSON 기록 구현**: 호출 횟수, 실패 종료와 `runs/*.json`을 가짜 응답으로 확인한다. 기록은 이 단계의 실행 결과를 그대로 사용한다.
4. **Textual TUI 탭 붙이기**: 이미 모인 실행 데이터를 탭에 표시하고 비동기 실행 중 완료된 역할부터 갱신한다.
5. **설정만으로 역할 변경·추가 검증, 비밀값·오프라인 테스트 확인**: 기존 경로를 새 역할이 그대로 쓰는지 확인하고 공통 합격 조건을 검사한다.

## 5. 초기 확인 항목과 현재 결정

| 항목 | 현재 결정·제한 |
| --- | --- |
| 검토 응답 계약 | 첫 줄 `PASS`/`FIX`; `FIX`에는 후속 의견이 필수다. 형식이 잘못되면 재시도 없이 실패한다. |
| 재검토 이후 흐름 | 두 번째 검토의 유효 판정이 `PASS`이면 다음 역할로 진행한다. `FIX`이면 Editor를 호출하지 않고 실패를 기록한다. |
| 추가 역할 | `crew.translator.yaml`은 Editor 뒤에 Translator를 두고 `editor.output`을 전달한다. |
| 입력·출력 인터페이스 | 질문 문자열과 선택적 `--plain`, `--config`; TUI에는 질문 입력칸이 있다. |
| 기록 방식 | `runs/*.json`에 역할별 결과를 기록하고 키·Bearer 값·이메일·한국 전화번호·주민등록번호 형태를 마스킹한다. 이름·주소 등 모든 개인정보는 자동 탐지하지 못한다. |
| 시간 측정 | LLM 호출 시간을 초 단위로 측정해 역할별로 표시·기록한다. |

플레이스홀더 검사는 지정된 대괄호 표제만 판별한다. 미정 사실을 사전 안내로 표현할지와 질문에 없던 사실을 만들어냈는지에 대한 모든 판단을 코드가 보장하지는 않는다.

## VIBE-Q와 비교 결과

- **누락된 요구**: `crew.yaml`의 역할별 입력 대상과 `max_revisions: 1`, `--plain` 실행, Textual의 비동기 탭·질문 입력칸, 역할별 입력·출력·시간을 담는 `runs/*.json`을 R1~R5에 반영했다. 검토 응답은 첫 줄 `PASS`/`FIX` 형식을 채택하고 잘못된 응답의 실패 처리를 명시했다.
- **추가로 정의한 요구**: 초안의 설정 오류 사전 검증, 실패 실행 기록, 키의 터미널 출력 방지와 상태·종료 정보는 VIBE-Q 표보다 구체적이다. 구현 범위를 늘리는 별도 기능으로 보지 않고 기존 요구의 검증 조건으로 유지한다. 웹 화면·계정·원격 검색과 무제한 수정 루프도 초안에서 추가로 범위 밖에 명시한 항목이다.
- **구현 순서 차이**: 초안은 화면과 기록을 같은 단계에 두었으나 VIBE-Q는 검토·재작성과 함께 기록을 만들고 그다음 TUI를 붙인다. 3단계에서 실행 데이터와 JSON 기록을 먼저 완성하고 4단계에서 TUI를 붙이도록 맞췄다. 설정·응답 계약을 먼저 정하고 가짜 LLM으로 검증하는 순서는 유지했다.
